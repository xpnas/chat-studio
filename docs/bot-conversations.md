# Configured BOT conversations

BOT support is **enabled by default** after joint conversation/history acceptance. Build with `--dart-define=STUDIO_BOTS=false` to close it independently. On 2026-11-13 the user approved acceptance using a deterministic local model driving the pinned real Studio runtime and local Android emulator. Real models remain unverified; iOS testing was waived and is not claimed to pass. This validates protocol, execution, persistence and mobile behavior within that scope, not model quality.

Configure at least two BOT conversations, their models/workspaces and an execution Agent preset in Studio before collaboration testing. The mobile client lists account-owned BOTs and can create a new BOT conversation with a name, authorized model and optional workspace. Leaving the workspace empty asks Studio to provision it. Execution Agent presets and other shared settings are still configured in Studio. BOT ownership is independent of the ordinary chat Profile. Resource ACLs still apply. Private worker sessions are available through task details and never become ordinary chat or automatic-read entries.

Open **Conversation history → BOT**, alongside the single-chat and group-chat tabs, to create, search, page and switch BOT conversations. The new-conversation button, search position above the tabs and list spacing match the single-chat tab. In a BOT conversation, swipe right across the reading area to open the same conversation drawer as ordinary chat, with the BOT tab selected. All single/group/BOT/history tabs remain available there. Swipe left to show active collaborations, background tasks and read-only configuration. Header buttons provide the same navigation. Drafts stay attached to their BOT when either panel opens.

The input surface and message body use the exact ordinary-chat components: ChatComposer, MessageBubble, AttachmentTile, AttachmentViewer, AudioAttachmentControl and ChatHistoryList. Single, group and BOT pages also share ChatBody, ChatReadingState, ChatReadingLayout and ChatConnectionLine: the same safe area, width, composer folding, floating reading progress, stop position, latest-message animation and new-content badge. Markdown, assistant segment grouping, attachment actions and latest-at-bottom scrolling therefore share the same presentation. Collaboration cards remain explicit boundaries between assistant turns. Live replies and peer-device input appear immediately, including while the keyboard or content height changes; reading older pages still requires explicitly returning to latest. Tap the model in the BOT composer to select from the account-authorized BOT catalog. Profile/provider/model identity and the server API protocol are retained, including identically named models across Profiles. Saving uses the BOT configuration revision; an active reply, conflict or revoked access prevents a silent overwrite. Failed writes refresh the authoritative snapshot and are never automatically replayed. Ordinary Agent preferences, reasoning controls and command suggestions remain separate. Each BOT keeps its own draft and projected history within the server/account boundary. Main-chat run/stop/resume use the original BOT ID and saved server configuration. A new-conversation request includes the observed defaults revision; an unknown creation result requires checking the refreshed list before another creation. Ordinary Agent model preferences are absent from these requests. Main-chat stop does not stop background work; task and collaboration controls are separate explicit actions.

Pending durable approvals/questions are deduplicated across events and snapshots. Durable questions have no local expiry countdown. Approval offers a single grant or rejection, never a forbidden permanent grant. Version conflicts and another device's answer refresh the pending state. Reconnecting does not answer questions automatically.

Task details separate current and historical executions, acceptance state, authorized results and pending input. Historical executions are read-only. Follow-up/stop bind task revision and the observed execution. An uncertain request retains its original idempotency key and payload; refresh first, then explicitly retry the original operation if needed. Editing the payload cannot reuse an unresolved key. Queue editing is not exposed.

The collaboration form selects existing BOTs, title/overall goal, stage goals and expected returns. It allows 1–13 stages and 1–1000 finite rounds. Groups start at 0 and remain contiguous; equal groups run in parallel. Duplicate members in a group and self-handoff, including a repeated round boundary, are rejected. A route preview precedes creation. Existing `round_limit=0` flows can be viewed and controlled; the mobile form does not create infinite loops.

Cards show flow, group/round, delivery, confirmation and error state. A reply is not a server-confirmed completed stage. Controls expose stop/resume, preserve revision/key preconditions and withhold resume while stopping. Completed flows have no control. Result details use their independent cursor and `history_key`, including visible-empty pages that still have a next cursor. Hidden tool/thinking history is never reconstructed into the main conversation.

Main history uses only `person-display-v1`: mixed `(kind,id)` references, messages and flow cards under one opaque cursor. A card-only page is not an empty conversation. Latest conditional-cache pages and old reading windows stay distinct, with at most 300 unique mixed references in total. Cache publication is atomic and scoped by server/account/BOT/projection; details also have a bounded page window. A missing/corrupt conditional page requests an empty cache ID. Projection/history changes invalidate old pages without discarding drafts. Returning to latest is explicit while reading older history.

Read ACKs require a persisted numeric assistant message actually painted in the visible latest viewport. Flow IDs, timestamps, raw totals and timeline cursors are never substituted. Unknown/unseen attention keeps unread state. Logout/server/account changes release active references; cache files cannot cross account scopes.

Rollback: build with `STUDIO_BOTS=false`. Existing server tasks and flows remain under Studio control; hiding a mobile entry does not stop, delete or recreate them.
